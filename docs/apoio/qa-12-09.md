## 🔴 Achado 1 — o deploy regrediu produção um mês (CORRIGIDO)

**Sintoma:** logo após o deploy, três rotas passaram a devolver 404 em
produção, incluindo `/api/estado-cozinha` — a faixa de estado que é o hero
do painel. Também `/api/lista-compras` e `/api/receitas-premium`.

**Causa raiz:** `railway up` executado de dentro do worktree
(`.claude/worktrees/...`) empacota a **raiz do repositório**, não o
diretório atual. E a raiz (`C:\Users\Usuario\alura-produto-ficticio`)
estava na branch **`ensaio-aula4`**, parada no commit `c311761`, de
**13/08** — anterior à v4 e à fase 5.

Ou seja: produção rodava código de 13/08, que **não tem**
`intencao-efeitos.js`, nem lista de compras, nem faixa de estado.

**Correção aplicada:** o worktree voltou para a branch de trabalho, a raiz
foi para `master` atualizado, e o deploy foi refeito de lá. Produção
confirmada em 13/13 rotas depois disso.

> ### ⚠️ Regra que vale de agora em diante
>
> **Nunca rodar `railway up` de dentro do worktree.** Sempre:
>
> ```bash
> cd C:/Users/Usuario/alura-produto-ficticio
> git checkout master && git pull
> railway up --service chef-caseiro --detach
> ```
>
> E conferir depois, porque o sintoma é silencioso:
>
> ```bash
> curl.exe -s -o NUL -w "%{http_code}\n" -u USUARIO:SENHA https://chef.workshopee.com.br/api/estado-cozinha
> ```
>
> **200 = deploy correto. 404 = subiu código antigo.**

**Desde quando produção estava assim:** pelo menos desde o deploy de 29/08,
feito da mesma forma. Isso explica um mistério — ver o achado 2.

## 🔴 Achado 2 — o cenário da lasanha está mais frágil do que parecia

### O que foi encontrado

Existe um relato de **29/08** no feed: *"Comeram lasanha, no total de 3
porções entre os dois"* — `fonte_refeicao: caseira`. E o estoque continua
**5/5**.

Isso levantou a suspeita de que a explicação do curso (o match falha por
`lasagna` × `lasanha`) estivesse errada. **Não está** — mas a história é
mais rica do que o script conta hoje.

### O trace revela duas coisas

Trace `724d2cf3a53efbfa29ad53fde19a3cda`, de 29/08:

```
ENTRADA:  "comemos a lasagna, num total de 3 porções nós dois."
SAÍDA:    { "item_nome": "lasanha", "item_quantidade": 3,
            "fonte_refeicao": "caseira" }
```

**Primeiro:** a entrada veio com `lasagna` (grafia errada) e o modelo
**normalizou para `lasanha`** — a grafia correta, que casaria com o estoque.
Em 22/08, com entrada praticamente idêntica, ele havia extraído `lasagna`
cru. Mesmo modelo, mesmo prompt, comportamento diferente.

**Segundo:** mesmo com o nome correto, o estoque não baixou — porque o
código em produção naquele dia era o de 13/08, que **não tinha a lógica de
baixa por relato** (achado 1).

### Por que isso importa para a gravação

1. **O episódio C (22/08) continua válido e verificável.** A evidência está
   preservada em `evidencia-preservada.md` e o trace ainda está no Langfuse
   até ~21/09.

2. **Ele provavelmente não reproduz mais ao vivo.** O modelo normaliza a
   grafia agora. Se você tentar recriar o caso hoje, o match tende a
   funcionar e o estoque tende a baixar. No formato linear isso não é
   problema — o caso é contado com evidência, não reproduzido.

3. **⚠️ E agora existe um risco novo para a prova visual.** Com o código
   correto em produção, **qualquer relato de lasanha no Telegram vai baixar
   as porções** — e as "5 de 5" que o vídeo 4.4 mostra na tela deixam de
   existir. Até hoje isso não acontecia, porque o código em produção era
   antigo.

   **Recomendação: não mandar relato de lasanha no grupo até terminar de
   gravar.** Se as porções baixarem, dá para restaurar o valor no banco,
   mas é melhor não precisar.

4. **Isso virou conteúdo melhor do que era.** "O mesmo modelo, com o mesmo
   prompt, mudou de comportamento entre 22 e 29 de agosto, sem ninguém
   alterar uma linha" é exatamente a tese da Aula 1, agora com trace dos
   dois lados. Vale considerar acrescentar ao vídeo 3.4 ou 4.4.

## 🟡 Achado 3 — o terceiro eixo não está na interface

O `RUNBOOK` e o material prometem **três eixos trocáveis ao vivo**:
`model`, `modelIngestao` e `modelVisao`.

- `GET /api/config` **expõe** `modelVisao` ✅
- A gaveta de Configurações tem **apenas dois** seletores ❌
- `public/app.js` só envia `model` e `modelIngestao` no POST

Ou seja: o eixo de visão só é trocável por API, não pela tela. Se a aula
disser "olha os três eixos aqui", a tela mostra dois.

**Esforço para corrigir:** pequeno — um `<select>` no HTML e dois pontos em
`app.js`. **Não apliquei**, pela convenção de perguntar antes de mexer em
algo que pode ser conteúdo (e porque muda a UI que aparece na gravação).

## 🟡 Achado 4 — erro de usuário classificado como erro de servidor

`POST /api/notas-fiscais/sefaz` com URL não-`.gov.br` **rejeita corretamente**
— a validação funciona e a mensagem é clara:

```
"URL invalida: espero o link do QR code da NFC-e (dominio .gov.br
 com a chave de acesso de 44 digitos)."
```

Mas responde **HTTP 500**, quando deveria ser **400**. O comportamento está
certo; a classificação está errada.

É pequeno, e é justamente o tipo de coisa que um curso de observabilidade
deveria notar: erro de entrada do usuário contado como falha do servidor
**polui a taxa de erro** do dashboard. Um alerta de "5xx subiu" dispararia
por alguém ter colado um link errado.

**Não corrigi** — mesma convenção. Mas aqui há um bônus: se corrigir, vira
um exemplo honesto de "o QA do curso encontrou um problema de
observabilidade no próprio produto do curso".
